## 历史训练流程恢复到了什么程度

主线是：教师模型生成并筛选解答/代码 → 两类监督样本 → Qwen3-4B-Base 的 LoRA SFT → 合并权重 → 执行生成的 Python 并比较数值答案。June 的 GRPO 材料是早期探索分支，November 的 SFT 论文与主 notebook 才是这次工程的主要依据。

恢复的数据链是：

- 算术 JSONL：309 条，训练目标使用代码字段。
- 蒸馏 JSONL：1,125 条 → 251 条内容/正确标记合格。
- 使用保存的提示词、聊天模板以及固定官方 tokenizer 版本过滤：251 → 143 条。
- 合计 309 + 143 = **452 条**，与历史训练日志一致。

此次 tokenizer 版本为官方 `Qwen/Qwen3-4B-Base` 的 `906bfd4b4dc7f14ee4320094d8b41684abff8539`。这说明公开版本能够重建相同数量和一份明确的样本成员列表；旧 Kaggle 的 tokenizer 文件和原模型权重没有恢复，因此不能说已经认证了原运行的每个二进制文件。

历史代码记录的是 float16、`load_in_4bit=False`、LoRA rank 32 / alpha 64、7 个投影层、batch size 1、梯度累积 8、学习率 `3e-5`、warmup 10、2 epochs、114 optimizer steps。论文中的部分 QLoRA、batch 64、`2e-4` 描述与这些可执行设置不一致。工程依据可追溯代码记录参数，并在说明中保留差异。

新的实现使用 Transformers/PEFT，显式采用 2,048 tokens 以内的完整序列训练。原 notebook 虽在预过滤时用了 2,048，但 SFTConfig 没有明确填写 trainer 的 max_length，不能保证当时训练器之后没有截断。因此新实现是透明记录差异的重建，不承诺逐比特恢复旧 Unsloth 运行。

## 必须写清楚的评估问题

使用上述 tokenizer 重建的最终训练集中，原来 20 道推理评估题有 **5 道重复出现：CSV 第 5、12、13、14、20 行**。在 token 过滤之前的 251 条合格池里，这 20 道题全部能找到。仅看候选池会夸大最终重叠数量，因此报告采用最终保留成员核算的 5/20，并保留 tokenizer 来源限定。

这意味着项目的限制除了样本量小，还包括重建训练集与测试题重叠。旧的 60% → 75% 可以作为历史运行观察记录，不能据此声称严格独立测试集上的泛化提升。

| 类别 | 历史 baseline | 历史 merged | 当前证据强度 |
|---|---:|---:|---|
| 算术 | 14/20，70% | 17/20，85% | 论文记录；配对预测和具体 20 题身份缺失 |
| 数学推理/论文中的证明类 | 12/20，60% | 15/20，75% | 两份原 notebook 保存的配对结果；存在上述重建重叠问题 |

两项差值都是 **15 个百分点**，每 20 题里多答对 3 题。指标实际检查生成代码的数值输出，使用 `rel_tol=1e-3, abs_tol=0`；论文写的 `1e-6` 与代码不同。它没有形式化验证证明，也不检查每段推理是否成立。

进一步检查发现，251 条可用于这条 SFT 路径的蒸馏记录均标为 `COMPUTATIONAL`。所以 GitHub 更准确的定位是“算术与代码辅助数学推理”，避免把自动数值判分写成“证明正确率”。

## 新实验的数据划分

默认 `question_disjoint_v1` 会先将两份原始评估 CSV 中的全部题目从训练候选里排除，再按规范化题目去重。被隔离或重复的评估题也用于训练排除，不会回流进训练集。

数学 CSV 的 100 行只有 89 个不同题目。已知第 15 行题目附加条件与答案冲突，第 43 行把奇函数性质错误地当成单射使用；新评估先隔离这两题，保留 87 题。完整数学正确性仍未得到认证，这不是一个新收集的外部基准。

| 新实验阶段 | 算术 | 数学推理/代码 | 合计 |
|---|---:|---:|---:|
| 训练候选 | 309 | 127 | 436 |
| 固定 tokenizer/template 过滤后 | 309 | 63 | **372** |
| 评估题 | 100 | 87 | **187** |

训练与评估的规范化题目交集为 0。检查涵盖大小写、空白和特定格式差异；无法保证识别所有语义近似题，也不证明基础模型预训练时从未见过这些题。新模型必须在这份新训练集上重新训练，不能拿已经受旧数据影响的 checkpoint 冒充新实验。

所有题目有来源文件、原始行号、稳定 ID 和处理原因。原始数据没有改写；已知异常、去重和过滤在派生数据与报告中记录。算术参考答案还有一些隐藏运算数精度差异，在原 `1e-3` 容差下通过，不能笼统称作“14 条错误标签”。

## 提示工程如何保留

项目单独保留了两份原始 system prompt 和原始聊天模板，保留原有措辞、空白和特殊标记。

算术 prompt 要求 fenced Python 程序与数值结果；推理 prompt 要求解答过程和程序。原模板生成前缀包含 `<start_working_out>`，而训练目标不总是使用同样标签；这个历史设计也被保留和披露。

新的 base/merged 推理使用相同 prompt、模板、EOS、贪心解码、生成长度和题目列表。标准答案只给评分器，不放进模型输入。原评估 notebook 中有一个未执行过的 prompt 清空 cell；直接 Run All 会改变条件，所以项目提供独立命令入口，避免依赖旧 notebook 的交互状态。

## 已完成并实际检查的工程

- `fyp.prepare`：生成固定训练/评估文件、排除与去重记录、哈希。
- `fyp.tokenize`：只下载 tokenizer 即可核算保留样本，不需要加载 4B 权重。
- `fyp.train`：LoRA 训练，记录设置、版本、实际样本顺序和输出 adapter。
- `fyp.merge`：核对 adapter 的 base 来源与版本，再合并并保存 tokenizer/config。
- `fyp.evaluate`：保存每题原始回答和完整运行条件；默认暂不执行生成代码。
- `fyp.score`：在 Docker 中隔离执行、限定资源/超时并评分。
- `fyp.compare`：核对题目、提示词、生成参数、计算精度、运行环境、Docker 镜像和评分条件，输出两类准确率及逐题变化。

**实际验证：24 项单元测试通过；随机初始化的小型 Qwen3 完成 2 个真实 optimizer steps，训练后模型输出发生变化，adapter 与 merged 的最大 logit 差约 `2.98e-8`；重新加载和一次推理成功。** 这个小模型没有作为数学评测对象，结果文件中 benchmark accuracy 为 null。

完整 187 题的 prompt 也用固定官方 tokenizer 做了长度检查，最长 252 tokens，符合默认总长度 2,048 / 最大生成 1,024 的预算。

当前环境没有 CUDA GPU 和 Docker，未运行完整 4B 训练、4B 推理或真实 Docker 评分。GPU 依赖和 Docker 镜像方案已给出，但显存是否足够、8-bit optimizer 与可选 4-bit 分支仍需在目标环境验证。不会把这些尚未完成的实验写成“复现成功”。

## 如何接着运行

解压项目包后先打开根目录 `README.md`，中文核查说明在 `docs/REVIEW_ZH.md`，完整环境和命令说明在 `docs/RUNNING.md`。固定数据已经包含在项目里，无须重新找旧账号。

接下来的实际实验路径是：在可用 GPU 环境安装指定版本 → 用固定官方 base 版本训练 → 合并 → 对同一份 187 题分别生成 base/merged 预测 → 在 Linux/WSL2 的 Docker 环境评分 → 自动比较。可以在 Kaggle 生成预测后，连同两个 sidecar 文件下载到另一台机器评分。

这一轮交付的是可供 GitHub 使用的完整项目包和证据说明。旧权重缺失使历史 checkpoint 不能直接复测；新训练能使用已恢复的数据重新进行，最终提升多少应以真实新结果为准。原始论文包含学号、签名等信息，全文未放入公开草稿；两位作者署名和原 notebook 的上游声明已保留。
