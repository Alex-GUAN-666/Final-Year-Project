## What the teacher and checker do

- Configured teacher alias is `qwen-coder-32b-fp16:latest` (`batch_generate_and_verify_v3_1.py:21`); the local SFT notebook describes a Qwen2.5-Coder-32B distillation dataset (cell 3). The alias alone is not a pinned model identifier or weight revision.
- Both classification and code-generation prompts receive the **problem and existing full solution** (`:27–67`, `:111`, `:135–137`). `expected_answer` is used separately by the heuristic classifier and answer comparison (`:107–108`, `:344–345`). There is no distinct `expected_answer` field inserted into the teacher prompt, but the supplied solution commonly contains the final answer. Thus describe this as **solution-conditioned code translation/distillation**, not an independent teacher solving blind from the question.
- Classification rules inspect the answer and can label empty/nonnumeric/long answers `NON_COMPUTABLE` (`:77–105`). The teacher classifier is only a fallback. A fallback response containing `COMPUTATIONAL` selects that class; otherwise it selects `PROOF` (`:107–115`). These are heuristic labels, not a formal task taxonomy.
- Only `COMPUTATIONAL` problems receive generated code and answer checking (`:333–349`). `PROOF` and `NON_COMPUTABLE` records are skipped with no correctness judgment. A solution longer than 3,120 characters (`1300 * 2.4`) is skipped before producing a record (`:24`, `:326–328`); some errors also skip a row (`:364–371`). Hence 1,125 saved records need not represent the first 1,125 source rows.
- `execute_safely` is only a name: the implementation executes the code in-process using unrestricted Python `exec`, then calls `solve` (`:147–159`). It has no isolation or resource limit. No such generated code was executed for this provenance audit.
- `compare_answers` first accepts exact string equality; otherwise it converts basic LaTeX, parses with SymPy, evaluates to 30-digit numeric precision, and checks absolute error `< 1e-9` (`:189–236`). Missing result/answer returns null; conversion failures return false. This checks an answer value. It does **not** validate every explanation step, prove a theorem, or establish soundness of a generated proof.

## Training selection

- `archive/notebooks/Qwen3_(4B)_SFFT_code_0811.ipynb`, cell 11, and uploaded Kaggle training notebook, cell 13, load all synthetic arithmetic records without using their `is_correct` flags. Distilled records enter the CoT+Code pool only when `is_correct`, `generated_solution`, and `generated_python_code` are truthy. They do not additionally require `problem_type == 'COMPUTATIONAL'` or deduplicate by question.
- Local cells 12–13 / uploaded Kaggle cells 15–16 build the system/user/assistant messages, filter using `len(tokenizer.apply_chat_template(messages, tokenize=True)) <= max_seq_length`, combine arithmetic and CoT+Code, shuffle with seed 42, then serialize using the chat template. The saved local result is 309 arithmetic plus 143 CoT+Code, drawn from 251 correctness-eligible distilled rows.
- There is no train/test split or explicit test-question exclusion in that preparation code. Checking the 251 eligible rows alone overstates training-set overlap. The subsequent reconstruction described below provides final membership under a frozen public tokenizer and the recorded template, while the original tokenizer artifact remains absent.

## Evaluation-file ancestry and scoring

- All 100 rows of `data/raw/random_samples_for_inference.csv` match a recovered JSONL record in **all four supplied fields**: question ↔ problem, answer ↔ expected_answer, generated Python code, generated solution. Therefore the evaluation CSV is a projection/subset of the recovered distillation pool, not an independently sourced dataset. No CSV sampling/export implementation or random seed was found in the supplied scripts/notebooks.
- Each of the historical first 20 questions has a correctness-eligible (`is_correct=true`) counterpart in the recovered pool. This is confirmed **source-pool overlap**, not proof that all 20 survived the training token filter; the subsequent reconstruction finds five surviving question identities. Some questions have multiple source records; question-level comparison is required even when one specific textual solution fails the length filter.
- Both historical evaluation notebooks, cells 12–13, use `df.head(num)` with `num_for_test = 20` and load `random_samples_for_inference.csv`. They read only the question and ground-truth answer from the CSV. The saved reference code/solution columns are not inserted into model messages. Ground truth is used afterward by the scorer.
- The scorer executes the first extracted code block, parses its output and ground truth using `Decimal`, then calls `math.isclose(..., rel_tol=1e-3)`; no separate absolute tolerance is configured. The prose explanation is not graded. Correctness flags therefore mean **numeric code-output accuracy**, including for questions requiring substantial reasoning, not formal-proof accuracy.

Preserve the supplied snapshot for reproduction and label regeneration from these scripts as a related recipe, not a byte-identical rebuild.
